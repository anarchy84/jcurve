# BACKEND-ORDER-01 — 랭크프리 서버 주문 연동

상태: 공통 서버 모듈 로컬 구현·독립 검증 완료 / Claude 최종 검토 대기 / 고객 주문·결제 화면 및 실주문 비활성

> **후속 확정:** 사용자는 고객별 랭크프리 계정 연결을 선택했다. 최신 생성·자격증명 계약은 [BACKEND-ORDER-02](BACKEND-ORDER-02.md)다. 이 문서의 74/484·독립13/386은 ORDER01 당시 버전의 증거로 보존한다.

## 사용자 결정과 범위

2026-10-27 사용자가 셀프마케팅 주문은 기존 랭크프리 주문 API로 연결하고 API 키는 서버에서만 사용하도록 지시했다. 서버 운영 반영은 대표 확인 후 별도 전달 예정이다. ORDER01에서는 공통 서버 연동과 모의 HTTP 검증을 구현했다. 후속 답변으로 **고객별 계정 연결**을 확정했고 ORDER02에서 반영한다.

소유: `app/Services/Rankfree/*`, `config/rankfree.php`, `tests/Feature/RankfreeClientTest.php`, 이 문서. ORDER01은 `.env.example`에 기본 꺼짐·빈 공용키 설정을 추가했으나 ORDER02에서 공용키 설정은 제거한다. 프론트·DB·로그인·결제·충전·정산·SEO 코드는 수정하지 않는다. 실제 키 열람·실제 주문·서버 배포·커밋·push는 실행하지 않는다.

## 확인한 외부 계약

출처: [랭크프리 공식 API 문서](https://rankfree.kr/developers#order), 2026-10-27 재확인.

- 고정 HTTPS 주소 `https://rankfree.kr/api/v1`, 서버 Bearer 인증, `order` 권한.
- 상품 목록 `GET /products`, 상세 입력 스펙 `GET /products/{id}`, 접수 `POST /orders`, 상태 `GET /orders/{orderNo}`.
- 생성 응답은 201·`pending`이다. 고객 안내는 ‘접수’이며 완료로 표시하지 않는다. 상태는 `pending`, `processing`, `completed`, `canceled`다.
- 주문은 API 키 소유 계정에 속한다. 고객 소유권 판정은 제이커브에서 별도로 구현해야 한다.
- 내부 숨김 필드는 API 응답만으로 구분할 수 없다. 운영자 확인을 받은 상품 ID·고객 필드 키만 설정으로 허용한다. 필수 파일 첨부 상품은 API 주문 불가다.
- 수량·기간·쿠폰·최종 금액의 확정은 랭크프리가 맡는다. 상품별 고정 수량·날짜 필드 규칙을 이 사이트에 복제하지 않는다.
- 주문 POST의 멱등성 키 지원은 문서에서 확인되지 않았다. 타임아웃·5xx·응답 손상 시 자동 재주문하지 않는다.

## 모듈 계약

1. API 활성화와 주문 전송 활성화를 분리하고 모두 기본 `false`다. 키·상품 허용표가 없어도 사이트의 기존 기능은 동작한다.
2. 원격 주소는 고정하고 리다이렉트·자동 재시도를 끈다. 키는 브라우저·응답·오류 메시지에 포함하지 않는다.
3. 승인 상품 ID와 고객 입력 필드 키는 `config/rankfree.php`의 `product_fields`로 제한한다. 초기 허용표는 비어 있으므로 실제로 주문 가능한 상품은 없다. API 상품 스펙을 읽었다는 사실은 판매 승인·입력 항목 검수 완료가 아니다.
4. 상품·주문 응답은 허용 필드만 추려 반환한다. 운영자 필드·상위의 미지 필드는 버린다. 사용자 입력으로 가격·소유자 ID·상태를 보내는 인터페이스를 제공하지 않는다.
5. 주문 생성 전 상품 상세를 다시 조회해 API 주문 가능·허용 필드 타입을 확인한다. upstream 422의 필드 키는 허용된 입력에 한해서만 전달하며 원문 메시지는 전달하지 않는다.
6. 주문 전송 후 연결 오류·5xx·리다이렉트·비정상 응답은 `submission_uncertain`으로 구분한다. 고객 화면의 ‘다시 주문’ 자동 실행에 연결하면 안 된다. 이 모듈은 요청 한 번의 재시도만 막으며 사용자 재클릭·작업 큐 중복을 막는 영속 멱등성 원장은 아직 없다.
7. HTTP 라우트·고객 주문 조회 화면은 추가하지 않는다. 계정 소유권과 결제·주문 승인 게이트가 없는 상태에서 서버 키로 주문을 공개하면 안 된다.

## 다음 통합 순서

상품·고객 필드 운영자 검수 → 주문 계정 주체 확정 → 고객 인증·주문 소유권 및 가격 동의 → 결제/잔액·중복 접수 원장 → Claude 주문 UI 데이터 계약 → 테스트 환경의 실연동 검수 → 대표 확인 후 서버 담당자 반영.

기획 D8의 ‘기존 콘솔 이동 추천’은 사용자 지시로 API 주문 방향이 구체화됐고 계정 주체도 고객별로 확정됐다. 실제 연결·결제·공개 범위는 후속이며, 공유 PLAN-FINAL 변경은 요청 큐로 Claude에게 전달한다.

## 서버 인터페이스와 현재 증거

현재 ORDER02에서는 인증 계층이 찾은 고객 자격증명을 `RankfreeClient::forCustomer($authenticatedCustomerId, $credential)`로 명시해 생성한다. 무인증 기본 클라이언트·Laravel 컨테이너의 직접 생성·공용키 fallback은 제공하지 않는다. 상세 경계는 ORDER02를 따른다.

| 메서드 | 반환 | 전제 |
|---|---|---|
| `products()` | 승인 상품의 요약 배열 | 서버 API 활성·키 필요. 비승인 상품은 반환하지 않음 |
| `product(int $id)` | 승인 상품 및 고객 입력 스펙 | 상품 검수 허용표 필요. 숨김·파일 필드는 반환하지 않음 |
| `createOrder(int $productId, array $fields = [], ?int $quantity = null, ?int $days = null, ?int $couponId = null)` | 서버 확정 주문 배열 | 전송 활성·허용 필드·상품 상세 재조회. POST 한 번 |
| `order(string $number)` | 상태·서버 확정 금액·검수 필드만 포함한 주문 배열 | **호출자가 고객 주문 소유권을 먼저 확인해야 함** |

고객 UI에 연결할 메서드·필드 이름은 Claude와 별도 합의한다. DTO 문자열은 신뢰 가능한 HTML이 아니므로 Blade에서는 기본 escaping을 유지한다. 예외는 `RankfreeException`의 `reason`, `httpStatus`, 허용된 `field`만 사용하고 원격 응답·Authorization·키를 로그나 화면에 출력하지 않는다.

- 변경 전 전체 **60 tests / 402 assertions**.
- 최초 구현자 주문 모듈 **11 tests / 54 assertions**, 전체 **71 tests / 456 assertions** 통과.
- 독립 재현 수정 후 주문 모듈 **14 tests / 82 assertions**, 전체 **74 tests / 484 assertions** 통과.
- 소유 PHP Pint 통과. 실제 서버 API를 호출한 수치가 아니라 HTTP fake 기반 계약 테스트다.
- 별도 검증 지시서: [BACKEND-ORDER-01-VERIFY](BACKEND-ORDER-01-VERIFY.md). 독립 공격·무력화 실험 중에는 제품 코드를 동결한다.
- 고객 계정·가격 동의·결제·잔액·쿠폰 소유권·로컬 주문 소유권·영속 중복 원장은 미구현이다. 이 모듈의 `order()`가 계정 간 접근을 안전하게 공개해 주는 것은 아니다.

## 독립 검증 1차 발견과 수정

1. 허용 메타데이터 키 아래에 중첩 객체를 넣으면 값이 그대로 반환되는 문제를 재현했다. 상품 메타데이터·고객 필드 정의·선택 옵션의 자료형과 지원 타입을 검사하도록 보강했다. 필수 FILE/IMAGE는 API의 `orderable` 값과 무관하게 전송을 차단한다.
2. 주문 상품의 id/title 키가 없으면 POST 뒤 PHP 오류가 나거나 GET에서 정상 반환되는 문제를 재현했다. 누락·잘못된 타입·id0을 거부하고 POST 이후에는 접수 불명으로 구분한다. 공식 계약상 두 필드는 nullable이므로 **키가 존재하고 값이 null인 경우**는 누락과 구분해 유지한다.
3. 각 실패 입력에 회귀 테스트를 추가했고 독립 검증자가 같은 공격 fixture를 재실행해 통과했다. 문서 검토나 구현자 테스트만으로 최종 합격이라고 판정하지 않는다.

구현·검증 시점 관측 브랜치 `main`, HEAD `0b8ee51`(2026-10-27 13:59:35 체크포인트). 이 세션은 커밋·push·브랜치 변경을 하지 않았다.

## 독립 검증 최종 결과와 인수인계

[독립 검증 결과](BACKEND-ORDER-01-VERIFY-RESULT.md)에 재현 입력·fixture·명령·출력·해시를 보관한다.

- 전체 **74/74 tests · 484 assertions**, 주문 모듈 **14/14 · 82 assertions**, 별도 공격 **13/13 · 386 assertions** 통과.
- 소유 Pint·PHP 문법4파일 통과. POST 응답/오류 15종의 행렬에서 preflight GET15회·POST15회만 관측해 자동 재시도0을 확인했다.
- 비활성 방어 임시 제거 시 exit2로 실패하고 preventStrayRequests가 외부 연결을 차단했다. 원문 SHA256 복구 확인 후 대상 테스트 exit0·최종 전체 테스트 통과. 실제 키·외부 API·주문·DB·서버 반영은 실행하지 않았다.
- 프론트·DB·결제·원래 SEO 기능을 변경하지 않았다. 모듈 기본 플래그와 상품 허용표는 비활성/빈 값 그대로다. 운영자를 대신해 임의 상품이나 키를 채우지 않았다.
- Q-009에 사용자 API 주문 방향·공유 기획 D8 정리·프론트 데이터 계약을 요청했고, Q-010으로 결과 최종 검토를 요청한다. Claude가 읽거나 최종 승인했다고 의미하지 않는다.

**계정 방향 확정:** 고객별 랭크프리 계정 연결. 고객 키 등록·암호화 저장·주문/결제/소유권/중복 원장·실제 키 검수·테스트 환경·대표 서버 승인까지 마친 뒤 공개 주문 화면을 연결한다. 서버 API 어댑터의 로컬 완료를 실제 주문 서비스 완성으로 보고하지 않는다.
