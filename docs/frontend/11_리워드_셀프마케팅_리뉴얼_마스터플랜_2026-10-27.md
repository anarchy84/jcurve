# 제이커브 리뉴얼 마스터플랜

작성일: 2026-10-27 · 상태: 대웅 검토용 제안 · 대상: 기존 `j-curve.co.kr`

**이번 산출물은 계획이다. 서비스 코드·기존 카피·성과 수치·미디어·서버 설정을 변경하지 않았다. 사이트 구현, 배포, 콘텐츠 발행은 이 계획 승인 이후 별도 작업이다.**

## 1. 먼저 결정할 방향

추천은 **회사 이름과 도메인은 제이커브로 유지하고, 리워드 네트워크·자체 앱·셀프마케팅을 첫 화면에서 연결하는 것**이다. 기존 SEO 서비스와 글은 계속 운영한다.

새로운 핵심 메시지는 다음과 같다.

> 앱을 만들고, 네트워크를 운영하고, 마케팅을 직접 실행합니다.
>
> 제이커브는 리워드 앱 개발부터 광고 송출, 셀프마케팅 운영까지 연결합니다.

“두 서비스를 다 한다”는 소개만으로는 약하다. **어디에 광고가 나가고, 사용자가 무엇을 하고, 집행 뒤 무엇이 달라졌는지를 증명하는 회사**로 만들어야 한다. 경쟁사보다 크다는 주장을 먼저 하기보다 운영 실체와 결과를 먼저 보여주는 전략이다.

“순위상승”은 카피와 검색 콘텐츠에 적극 사용한다. 다만 목표·실제 관측 결과·보장을 구분한다. 상품 주문 수량 보장과 검색 순위 보장도 구분한다. 순위상승이라는 단어를 쓰면 안 된다는 전제로 기획하지 않는다.

현재 Laravel 공개 라우트 목록에서는 sitemap·RSS·IndexNow 엔드포인트를 확인하지 못했다. 의존 패키지 설치나 기획서의 체크 표시만으로 구현·배포 완료로 간주하지 않는다. SEO 감사 도구가 있는 것과 홈페이지 자체의 SEO 메타·스키마가 완성된 것도 다르다.

현재 사이트 관측: [제이커브 공개 홈](https://j-curve.co.kr/). PHP 8.3 이상 조건은 [Laravel 13 공식 릴리스 문서](https://laravel.com/framework/docs/13.x/releases)에서도 확인했다.

### 2-2. 공개 검색 자산의 최소 범위

`robots.txt`에 Jetpack과 Rank Math 사이트맵이 함께 안내돼 있다. 아래 XML 6개를 파싱해 중복 제거한 **공개 주소는 39개**였다. 이는 전체 URL이나 구글 색인 개수가 아니다. 구버전·고립 페이지·이미지·사이트맵에 빠진 주소는 별도 수집해야 한다.

| 사이트맵 | URL 항목 수 | 비고 |
|---|---:|---|
| `post-sitemap.xml` | 3 | `/seo/한글슬러그/` 글 |
| `page-sitemap.xml` | 18 | 서비스·블로그·계정·장바구니 등 혼합 |
| `product-sitemap.xml` | 4 | 숍과 SEO 패키지 |
| `avada_portfolio-sitemap.xml` | 13 | 더미로 보이는 포트폴리오 경로 포함 |
| `category-sitemap.xml` | 2 | SEO·링크빌딩 카테고리 |
| `sitemap-1.xml` | 24 | 위 목록과 중복. 새 고유 URL은 없었음 |

참조: [robots.txt](https://j-curve.co.kr/robots.txt), [Rank Math 인덱스](https://j-curve.co.kr/sitemap_index.xml), [Jetpack 인덱스](https://j-curve.co.kr/sitemap.xml).

사이트맵 XML 응답의 `X-Robots-Tag: noindex`는 HTML 글 전체에 noindex가 있다는 뜻이 아니다. HTML 페이지별로 별도 확인한다.

### 2-3. 이미 활용할 수 있는 자체 앱 소개 자산

[제이커브 앱스](https://apps.j-curve.co.kr/)에는 앱 개발·광고·미션 제공 설명과 앱 목록, 스토어 링크, 운영 화면이 공개돼 있다. 새 홈페이지는 이 자산과 연결하면 된다.

그 페이지에 공개된 꼬꼬농장·당근캐시·머니트리·꿀꿀캐시·꾹테크·용돈캡슐·영테크·캐시팡팡·감자밭·에그머니·사임캐시 등은 **검증할 후보 목록**으로 삼는다. 공개 목록만 보고 모든 앱을 회사 소유의 활성 리워드 매체로 집계하지 않는다. 직접 소유·개발 납품·운영 대행·제휴 매체를 구분하고, 광고 송출 가능 여부와 스토어 상태를 확인한 뒤 표시한다.

## 3. 경쟁사·참고 사이트 20개 URL 조사

### 조사 범위와 한계

2026-10-27에 제공된 20개 URL을 웹 수집과 에고 브라우저로 1차 확인했다. 제목·메뉴·헤딩·주요 본문·CTA·공개 링크를 중심으로 비교했다. 유료 가입·주문·충전·개인정보 입력은 하지 않았다. 초기 DOM과 검색 수집 결과만으로 실제 성능이나 상품 품질을 판정하지 않는다.

**REA 번들 분석은 미실시다.** REA의 웹 분석 도구는 로컬 CDP 주소와 대상 ID가 필요한데, 현재 에고 연결에서는 사용할 수 있는 로컬 CDP 리스너를 확인하지 못했다. 에고의 `Browser.getBrowserCommandLine` 호출도 지원되지 않았다. 브라우저 DOM 추출을 ‘REA 디컴파일 완료’로 부르지 않는다. 공개 서버 응답에서 PHP·DB·비공개 주문 엔진이 복원되는 것도 아니다.

제공된 URL이 20개라는 것이 독립 경쟁사 20곳이라는 뜻은 아니다. NBT·애디슨 관련 사이트는 같은 기업군의 서로 다른 접점이다. OK캐쉬백 적립 화면은 소비자 참여 UX 참고, DARO는 수익화 인접 경쟁 참고다. 랭크프리는 로컬 기획에 자사 솔루션으로, 쇼피트렌드는 현 제이커브 사이트에 연결 플랫폼으로 표시돼 있다. 대외 비교표를 만들기 전 사업 관계부터 확정한다.

| 용도 | 사용할 문장 | 필요한 근거 |

| 목표 | 순위상승을 위한 플레이스 셀프마케팅 | 무엇을 집행하고 무엇을 측정하는지 설명 |

‘순위상승’이라는 단어 자체를 금지하는 공식 근거는 이번 확인 범위에서 찾지 못했다. 다만 네이버는 다계정 동원·방문 및 추천 조작·자동 트래픽 부풀리기를 스팸 사례로 설명한다. 상품 동작의 적합성은 단어 선택과 별도로 확인해야 한다. [네이버 공식 스팸 사례](https://searchadvisor.naver.com/guide/content-abusing)

## 5. 메뉴와 검색 의도를 함께 설계한다

메뉴를 새로 꾸민다고 기존 페이지 주소까지 바꿀 필요는 없다. 고객에게 보이는 메뉴명과 내부 URL은 분리해 생각한다.

### 5-1. 추천 상단 메뉴

**리워드 네트워크 · 셀프마케팅 · 자체 앱 · 성과 사례 · 인사이트 · 회사소개**

상시 버튼: **시작하기 / 상담하기**

SEO·퍼포먼스·CPA·개발 서비스는 ‘전체 서비스’ 보조 메뉴와 관련 페이지 본문에서 직접 연결한다. 기존 `/seo/`를 푸터 깊숙이만 숨기지 않는다. 모바일에서도 두 번 이내 선택으로 접근하도록 한다.

### 5-2. URL·고객·CTA 제안

| 페이지 | 주소 제안 | 고객의 질문 | 핵심 CTA |
|---|---|---|---|
| 홈 | `/` 유지 | 이 회사는 뭘 직접 하는가 | 셀프 시작 / 광고·매체 상담 |

| 매체사 | `/services/reward-network/publishers` 신설 후보 | 연동 방식·운영·정산은 어떤가 | 매체 제휴 문의 |

신규 후보 URL은 아직 만들지 않았다. 기존 SEO 세부 페이지와 셀프마케팅의 플레이스·쇼핑 페이지가 같은 키워드를 놓고 경쟁하지 않게 검색 의도를 먼저 나눈다. ‘플레이스 마케팅 전략·대행’과 ‘플레이스 리워드 직접 주문’이 실제 검색 결과에서 구분되지 않으면 별도 페이지를 양산하지 않고 기존 강한 페이지의 섹션으로 시작한다.

### 5-3. 홈의 권장 순서

| 순서 | 섹션 | 전달할 내용·증거 |
|---|---|---|
| 1 | 한 문장 소개 + 목적 선택 | 셀프마케팅 / 광고 집행 / 앱 수익화 3개 진입점 |
| 2 | 직접 운영하는 구조 | 광고 설정 → 네트워크 송출 → 앱 참여 → 결과 확인 |
| 3 | 실제 앱과 미션 | 공개 가능한 앱 3~5개의 실제 화면·스토어·참여 과정 |
| 4 | 목적별 상품 | 플레이스·쇼핑·앱 설치·가입 등 실제 제공 범위 |
| 5 | 직접 집행 절차 | 상품 → 조건·예산 → 접수·승인 → 진행·결과 |
| 6 | 성과 사례 | 최소 검증 사례부터. 가상 상승 그래프를 실적으로 표시하지 않음 |
| 7 | 네트워크·기술 운영 | 매체 구분, 완료 인정, 중복 방지, 연동·정산 방식 |
| 8 | 기존 전문성 | SEO·퍼포먼스·CPA와 보유 솔루션 연결 |
| 9 | 최신 인사이트 | 실험·운영 데이터·가이드의 최근 글 |
| 10 | 목적별 최종 CTA | 셀프 시작 / 광고 문의 / 매체 제휴 |

기존 힉스필드 미디어와 디자인 토큰을 먼저 재사용한다. 영상이 서비스를 이해시키지 못하면 실제 제품·앱 화면에 우선순위를 준다. 첫 화면의 회사 설명·링크·헤딩은 영상 속 글자가 아니라 HTML 텍스트로 제공한다. 모바일 영상 자동 재생·모션 축소·초기 이미지·레이아웃 공간 예약을 함께 설계한다.

### 5-4. 상세 페이지의 기본 골격

네트워크 광고주 페이지: 대상 행동 → 실제 송출 매체 → 과금·인정 기준 → 운영 과정 → 성과 사례 → 문의.

매체사 페이지: 제공 중인 연동 방식 → 사용자 참여·보상 과정 → 운영·정산 안내 → 실제 도입 화면 → 기술 문의. 개발 문서는 존재하는 API·SDK와 일치하는 것만 연결한다.

셀프 상품 페이지: 대상 고객 → 수행 행동 → 단가·최소량·기간·세금 안내 → 입력 예시 → 진행·취소 조건 → 결과 지표 → 주문 진입. 가격이 확인되지 않았으면 0원·가짜 최저가를 표시하지 않는다.

## 6. 기존 구글 노출을 지키는 이관 순서

기존 도메인을 계속 쓰는 방향은 적절하다. 다만 도메인 연령·외부 DA/DR만으로 검색 우위를 확정할 수는 없다. 실제 보호 대상은 **노출·클릭·백링크·전환이 있는 URL과 내용**이다. 이번에는 GSC·애널리틱스·서치어드바이저 계정 데이터에 접속하지 않았으므로 현재 상위 글·트래픽·도메인 점수를 확정하지 않는다.

### 6-1. 1단계 — 검색 자산 원장을 먼저 만든다

다음 데이터를 합쳐 URL별 행 하나로 만든다.

- GSC 최근 16개월의 페이지·쿼리 실적과 최근 90일·28일 비교. 브랜드/비브랜드, 기기, 국가를 나눈다.
- GA4 등 기존 분석 도구의 유입 랜딩·전환과 현재 태그/전환 정의.
- 네이버 서치어드바이저의 수집·색인·검색 현황과 제출 피드.
- 사이트맵·내부 링크 크롤링·서버 로그·백링크 유입·구버전 경로.
- title·description·canonical·robots·H1·핵심 본문·이미지·발행일·수정일·내부 링크·HTTP 상태.

원장 필드는 `원URL / 유입쿼리 / 클릭·노출 / 전환 / 외부링크 / 현본문 / 유지·변경사유 / 최종URL / 기대상태 / 담당 / 승인 / 검증결과`로 고정한다. ‘확인 못 함’을 0으로 채우지 않는다.

공개 주소 39개와 저장 원문 50+3개는 이 원장의 출발점이다. 합산 숫자를 색인 개수처럼 발표하지 않는다.

### 6-2. 2단계 — 주소를 세 부류로 나눈다

| 부류 | 처리 | 판단 기준 |
|---|---|---|
| A. 실적·백링크·관련성이 있는 기존 주소 | **원URL 200 유지 우선** | 제목·핵심 내용·검색 의도·내부 링크를 보존 |
| B. 변경 필요 또는 중복 통합 | **동등한 내용의 최종URL로 1회 301** | 본문 이식과 도착지 200 확인 후 승인 |
| C. 계정·장바구니·더미·완전 폐기 후보 | **개별 판단** | 검색 성과·고객 기능·연결을 확인. 무관한 홈 전송 금지 |

아무 대응 콘텐츠도 없는 더미를 홈·성과 사례로 일괄 전송하지 않는다. 실제 폐기 대상으로 확정된 경우에만 404/410 등 적절한 상태를 선택한다. 이번 계획 단계에서는 어떤 페이지도 삭제하지 않는다.

### 6-3. 현재 알려진 주소의 처리 제안

| 기존 주소 | 8월 문서의 안 | 이번 추천 |
|---|---|---|
| `/seo/` | `/services/seo`로 301 | 원URL 200 유지 우선. 중복 본문 주소는 canonical·301 정책 하나로 정리 |
| `/seo/기존-글-슬러그/` 3개 | `/insights/동일슬러그`로 이동 | 원URL 보존 우선. 인사이트 목록에서 기존 주소를 직접 연결할 수 있음 |
| `/seo-backlinks/` | `/services/seo/backlinks`로 301 | 실적·내용 확인 후 보존 우선 |
| `/naver-place-marketing/` | SEO 하위로 301 | 실적 보존 + 셀프마케팅과의 검색 의도 조정 |
| `/naver-shopping-marketing/` | SEO 하위로 301 | 실적 보존 + 직접 주문 경로 연결 |
| `/wordpress-agency/` | `/services/wordpress`로 301 | 관련 내용·사업 유지 여부 확인 후 보존 |
| `/blog/`, 두 카테고리 | 인사이트로 통합 | 기존 실적 확인 후 유지 또는 정확한 카테고리로 개별 301 |
| `/shop/`와 SEO 패키지 | 부스팅샵·상품으로 이동 | 구상품과 새상품의 동일성 확인. 무관한 리워드 상품으로 전송하지 않음 |
| `board.php?bo_table=column&wr_id=…` | 칼럼별 301 | 원문 단위 이관. 파라미터 순서·추가 UTM·한글 인코딩을 검증 |
| `/v1/`·기존 PHP 랜딩 | 서비스별 301 | 현 유입과 내용이 맞는 목적지로 개별 매핑 |
| Avada 포트폴리오 경로 | `/work` 일괄 301 | 더미·백링크·실적 확인 후 개별 결정으로 수정 제안 |

**URL을 바꾸지 않아도 홈의 주제·내용 변경으로 순위는 달라질 수 있다.** 특히 현재 홈이 SEO 쿼리를 많이 받고 있다면 새 홈 카피와 title 전환을 별도 단계로 나누고 `/seo/`의 전문성과 연결을 먼저 보강한다.

### 6-4. 3단계 — 새 디자인을 비공개 환경에서 검증한다

개발 환경은 인증 보호를 기본으로 하고 noindex를 보조로 사용한다. robots.txt 차단만으로 비공개·색인 방지를 대신하지 않는다. 원문은 실제 HTML로 렌더링하고, 기존 콘텐츠 보존과 신규 섹션을 대조한다.

검수는 URL→최종 응답만 보지 않는다. title·본문·canonical·이미지·구조화데이터·링크·모바일 접근을 함께 확인한다. 스테이징 주소가 canonical·사이트맵·공유 메타에 섞이면 실패다.

### 6-5. 4단계 — 승인 후 제한된 범위로 공개 전환한다

도메인·CMS·URL·본문·브랜드를 전부 한 번에 변경하지 않는다. 권장 순서는 아래와 같다.

1. 기존 URL·본문을 유지하는 Laravel 호환과 보호 장치를 검증한다.
2. 신규 리워드·셀프 상세와 자체 앱 증거를 추가한다.
3. 홈의 배치·카피·title을 확정된 검색 데이터에 따라 전환한다.
4. 정말 필요한 URL 변경만 별도 매핑 배치로 처리한다.

공개 당일 인증·noindex 제거 대상, robots, canonical, sitemap, 캐시·CDN·리다이렉트·문의·주문 연결을 검증한다. 기존 태그와 전환 정의도 이어받는다. 같은 도메인 내 경로 변경이므로 도메인 이전용 Change of Address 절차를 기계적으로 적용하지 않는다.

301은 최소 1년 유지하고 가능하면 장기 보존한다. 무관한 홈으로 전송하거나 짧은 기간만 유지하지 않는다. 회복 시점은 사이트별로 다르므로 **‘2~4주 회복’은 약속하지 않는다.** [Google 사이트 이동 공식 문서](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

### 6-6. 5단계 — 공개 후 8주 집중 관측

- 첫 72시간: 핵심 URL·5xx·404·잘못된 noindex·canonical·문의/주문 기능을 매일 확인.
- 1~2주: 보호 URL의 수집·색인·페이지별 클릭·노출과 리다이렉트 로그 확인.
- 3~8주: 7일·28일·전년/동요일·브랜드/비브랜드·기기 구분으로 비교.
- 이후: 301·기존 이미지 경로·검색 자산 유지 상태를 정기 확인.

운영 경보 제안: 핵심 URL이 200/합의된 301을 벗어나거나 잘못된 noindex·canonical이 생기면 즉시 조사한다. 충분한 표본이 있는 보호 페이지군의 7일 비브랜드 클릭이 기준 대비 20% 이상 하락하면 원인 분석을 시작한다. 이 수치는 내부 조사 트리거이며 검색엔진 공식 임계값도 회복 보장도 아니다.

롤백은 배포 버전·서버 라우팅·콘텐츠 스냅샷·DB 호환성·캐시를 묶어 준비한다. 실제 전환 실패 시 승인된 롤백 절차로 복구한다. 정상 페이지를 단지 검색 변동이 있다는 이유로 매일 되돌리지는 않는다.

### 7-3. 구조화데이터는 보이는 사실을 설명한다

- 회사: Organization, 일관된 법인명·브랜드명·로고·공식 연결 주소.
- 사이트: WebSite, 실제 대표 사이트명. 기존 제이커브 entity를 끊지 않는다.
- 글: Article/BlogPosting, 실제 저자·프로필·원발행일·수정일·대표 이미지.
- 경로: BreadcrumbList와 실제 화면의 탐색 경로 일치.
- 서비스: 실제 서비스와 적용 가능한 Service 정보. 스키마가 있다고 검색 순위를 보장하지 않는다.
- 앱: 실제 공개 앱 소개가 있을 때 해당 앱 정보와 공식 스토어 연결. 존재하지 않는 SDK에 SoftwareApplication을 붙이지 않는다.

자사 리뷰 별점·가짜 후기·허구 수상 이력·확인되지 않은 가격을 구조화데이터에 넣지 않는다. 지원 기능과 문법은 구현 시점의 공식 문서·검증 도구로 다시 확인한다.

### 7-4. 네이버는 웹문서·블로그·플레이스 목표를 구분한다

홈페이지의 목표는 브랜드 검색에서 정확한 기업 정보와 서비스 문서를 노출시키고, 관련 질문에 전문 출처로 발견되는 것이다. 고객 매장의 플레이스 순위를 올리는 서비스 KPI와 홈페이지 자체의 웹 검색 순위를 혼합하지 않는다.

서치어드바이저 소유 확인·수집 상태·사이트맵·RSS를 점검한다. 승인된 신규·변경·삭제 URL은 IndexNow로 알릴 수 있다. 접수 성공은 색인·상위노출 성공이 아니다. [네이버 IndexNow 공식 안내](https://searchadvisor.naver.com/guide/indexnow-about)

제이커브 원문을 기준으로 네이버 블로그에는 별도의 사례 해설·작업 과정·경험형 요약을 쓴다. 원문을 그대로 복제하는 자동 배포망을 만들지 않는다. 운영자·회사 정보와 주제 일관성을 유지한다. [네이버 콘텐츠 작성 권장사항](https://searchadvisor.naver.com/guide/content-basic)

블로그용 C-Rank·D.I.A. 설명을 기업 웹문서·AI 브리핑의 공개 순위 공식처럼 사용하지 않는다. 네이버 내부 알고리즘 가중치는 확인할 수 없다. 홈페이지 한 개만으로 모든 네이버 검색 지면 상단을 보장하는 계획도 세우지 않는다.

### 7-5. GEO의 실행 단위는 원천 정보다

AI가 인용할 만한 자료는 ‘리워드 광고란?’을 다시 요약한 글보다 다음과 같은 운영 자료다.

1. 실제 앱에서 미션을 발견하고 참여·보상을 확인하는 과정.
2. 상품별 행동·과금·완료 인정 기준의 비교표.
3. 캠페인 집행량과 순위·문의·구매 결과를 분리한 사례.
4. 측정 표본·기간·중복 제거·제외 조건이 있는 데이터 리포트.
5. 실패 사례와 수정 과정, 서비스별 적용 조건.

읽기 쉬운 결론·표·용어 정의·근거 링크는 독자를 위해 쓴다. 특정 글자 수·문단 쪼개기·AI 전용 스키마를 비공개 순위 공식으로 주장하지 않는다. 위 권고는 제이커브의 콘텐츠 전략이며 인용 보장 공식이 아니다.

검색봇 접근과 AI 학습 허용은 별도 결정이다. OpenAI의 `OAI-SearchBot`과 `GPTBot`은 역할이 다르며 검색을 허용하면서 학습은 거부할 수 있다. robots.txt와 CDN/WAF 양쪽을 확인한다. [OpenAI 공식 크롤러 문서](https://developers.openai.com/api/docs/bots)

Google은 Search Console의 Search generative AI 설정과 **Generative AI performance report**를 제공한다. 보고서는 Google AI Overviews·AI Mode의 노출을 다루며 데이터가 부족하면 보이지 않을 수 있다. ChatGPT·네이버 성과를 이 보고서와 합산하지 않는다. [포함 설정](https://support.google.com/webmasters/answer/16908024), [AI 실적 보고서](https://support.google.com/webmasters/answer/16984139)

ChatGPT·Perplexity·네이버 AI는 월별 고정 질문 세트를 같은 조건으로 확인하고 질문·날짜·지역·로그인 상태·응답·인용 URL을 기록한다. 수동 표본 관측을 전체 시장 점유율로 발표하지 않는다.

## 8. 검색어와 페이지의 역할

아래는 **검색량을 아직 측정하지 않은 초기 검색 의도 가설**이다. 규모·CPC·경쟁도·현재 순위는 입력하지 않았다. GSC와 네이버/광고 키워드 자료를 확보한 뒤 우선순위를 확정한다.

| 묶음 | 검토할 검색어 | 담당 페이지·목적 |
|---|---|---|
| 네트워크 | 리워드 네트워크, 리워드 광고, 리워드 마케팅, 오퍼월 광고, 보상형 광고 | 네트워크 허브·광고주 |
| 수익화 | 오퍼월 연동, 오퍼월 SDK, 앱 수익화, 앱 광고 수익, 리워드 매체 제휴 | 매체사 페이지. 제공 중인 방식과 일치 |
| 직접 집행 | 셀프마케팅, 셀프 리워드, 리워드 광고 단가, 리워드 광고 비용, 셀프마케팅 플랫폼 | 셀프 허브·가격/조건 |
| 플레이스 | 플레이스 마케팅, 플레이스 리워드, 플레이스 순위상승, 플레이스 순위 확인, 네이버 지도 상위노출 | 기존 랜딩·가이드·실행으로 역할 분담 |
| 쇼핑 | 스마트스토어 마케팅, 쇼핑 리워드, 스마트스토어 순위상승, 상품 순위 확인, 쇼핑 유입 | 기존 랜딩·상품 가이드 |
| 앱 광고 | CPI 광고, CPE 광고, CPA 광고, CPQ 광고, 앱 설치 광고 | 광고주·상품 설명 |
| 기존 SEO | 구글 SEO 업체, 네이버 SEO 업체, 검색엔진 최적화, 기술 SEO, SEO 컨설팅 | 기존 SEO 자산 보호·확장 |
| 브랜드·비교 | 제이커브, 제이커브 리워드, 부스팅샵, 리워드 광고 비교, 오퍼월 선택 기준 | 회사·실제 서비스·중립 비교 자료 |

키워드 한 개당 페이지 한 개를 기계적으로 만들지 않는다. 같은 문제를 해결하는 검색어는 한 페이지로 묶는다. 회사 이름·지역만 바꾼 얇은 랜딩 대량 생성도 제외한다. [Google 스팸 정책](https://developers.google.com/search/docs/essentials/spam-policies)

기존 홈의 검색 기여도가 높은 경우 title은 단계적으로 전환한다. 검토용 문자열은 `구글·네이버 SEO 및 리워드 마케팅 | 제이커브` → 최종 후보 `제이커브 | 리워드 네트워크·셀프마케팅`이다. 적용 시점은 GSC 분석 후 정한다. 이 문서는 즉시 교체 지시가 아니다.

## 9. 매일 콘텐츠가 쌓이는 운영 구조

### 9-1. 글을 매일 만드는 것보다 근거를 매일 모으는 구조

한 주의 운영 경험·데이터를 수집해 긴 사례 1개, 문제 해결 글 2개, 가이드 2개, 짧은 운영 메모·기존 글 업데이트 2개로 나눈다. 같은 자료를 제목만 바꾸어 7편으로 늘리지 않는다.

발행 목표는 하루 1건이다. 근거가 없는 날은 기존 글을 실제로 개선하고 변경 이력을 남긴다. 새 글 수를 채우려고 사실을 만들거나 이미 쓴 내용을 반복하지 않는다.

고정 흐름은 **주제 선정 → 자료 수집 → 초안 → 출처·상품·수치 검토 → 대웅 승인 → 발행 → 사이트맵/RSS/IndexNow 갱신 → 성과 확인**이다.

AI는 초안·요약·편집·오류 탐지에 사용한다. 서비스 코드나 스케줄러가 승인 없이 공개 상태로 바꾸지 못하게 한다. 예약 발행도 사전 승인된 버전에만 허용한다. 본문 변경으로 승인 대상 버전이 바뀌면 재검토한다. 이 발행 게이트는 프로젝트의 자동 발행 금지 규칙을 반영한 것이다.

AI 콘텐츠의 정확성·신뢰성 검토 방향은 [Google 생성형 AI 콘텐츠 공식 안내](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)와 맞춘다.

## 10. 개발 환경과 주문 연동

### 10-1. 기존 서버에 맞춘다

기존 PHP 8.3+/Laravel 13/Blade를 유지하고 MySQL·MariaDB 호환을 확인한다. Node는 프론트 빌드에 사용한다. Vite 8이 있는 만큼 **Node ‘22’라는 메이저 숫자만 확인하지 않고, 패키지·lockfile의 정확한 engine 조건과 서버 Node 마이너 버전을 대조**한다.

비밀값은 서버 환경에 두고 `.env.example`에는 이름과 설명만 둔다. README에는 실제 lockfile 기반 설치·빌드·마이그레이션·캐시·큐·스케줄·롤백 절차를 적는다. 이 단계에서 패키지를 무작정 최신화하거나 서버를 변경하지 않는다.

### 10-2. 초기 릴리스와 후속 주문 통합을 나눈다

1차는 **회사·상품 설명 → 기존 운영 콘솔의 정확한 상품·가입·주문 경로**로 연결하는 것을 추천한다. 현재 서비스의 로그인·충전·취소·정산을 그대로 활용하고 유입 출처만 보존한다.

2차로 홈페이지 안에서 주문을 받으려면 결제·충전 주체, API 키 소유 계정, 고객별 잔액·주문 소유권을 먼저 확정한다. 하나의 API 키로 여러 방문자의 주문을 처리하는 모델을 임의로 만들지 않는다.

### 10-3. API 원문에서 확인한 추가 조건

[랭크프리 주문 API](https://rankfree.kr/developers#order)를 직접 확인했다. 목록·생성·상태 조회 외에 `GET /products/{id}`의 입력 스펙이 중요하다. 생성 성공은 `pending` 접수 상태이며 운영자 승인 후 진행된다. 필수 파일 첨부 상품은 API 주문이 불가능할 수 있고, 상세 필드에는 사용자용과 내부용이 함께 내려와 응답만으로 숨김 여부를 구분할 수 없다.

따라서 후속 구현 계약에는 다음을 넣는다.

- 브라우저 → Laravel 서버 → 랭크프리. 서버에서만 키 사용.
- 승인 상품과 사용자용 입력 필드만 명시적으로 허용.
- 가격·할인·수량·기간은 서버 확정 응답을 기준으로 표시.
- 사용자별 로컬 주문 매핑과 소유권 검사. 주문번호만으로 타인 주문 조회 불가.

- API 오류·판매 중지·잔액·취소/환불·테스트 주문 허용 범위를 확정한 뒤 통합.

이번에는 API 키를 조회하거나 실제 주문을 생성하지 않았다.

## 11. 실행 순서와 승인 게이트

아래 기간은 자료 접근과 담당자 확보를 가정한 작업량 추정이다. 대웅의 검토·외부 서버 작업·상품 계약 대기 기간은 별도다. 신규 통합 결제·정산은 이 추정에 포함하지 않는다.

### 11-1. 승인 후 REA 상세 분석 작업 계약

현재 공개 DOM 조사에서 의사결정에 가장 중요한 대표 사이트를 선정한다: 애디슨·버즈빌·DARO·캐시플랜·셀프마케팅.com·쇼피트렌드. 상품·가격·블로그·공개 가입 진입까지 재현하되 주문·충전은 하지 않는다.

REA에서 접근 가능한 브라우저 연결 방식을 먼저 확보하고, 사이트별로 공개 DOM·스크립트·청크·경로 후보·네트워크 메타데이터를 수집한다. 원문 공개 범위에서 기술 구조를 확인하고, 실제 관측과 AST 기반 추론을 구분한다. 증거 ID·시각·URL·도구·누락 이유를 남긴다.

실제 백엔드·매출·미공개 로직은 복원됐다고 주장하지 않는다. 경쟁사 에셋·카피를 재사용하기 위한 분석으로 확대하지 않는다. 이 단계의 목표는 탐색 구조·설명 순서·전환 마찰·렌더링 특성을 우리 설계에 반영하는 것이다.

### 11-2. 구현 이후 필수 검수

- 보호 URL 전수: 승인된 원주소 200 또는 필요한 1회 301 후 200. 루프·체인·무관한 목적지 0건.
- 중요 본문: 제목·핵심 설명·이미지·발행일·성과 수치·고지 손실 없음.
- 검색 설정: 공개 페이지의 잘못된 noindex·개발 canonical·로그인 강제 없음.
- 피드: 검색 대상 목록·발행일·canonical이 화면과 일치.
- 화면: 주요 모바일 폭에서 CTA·상품 조건·문의 가능. 모션 축소·키보드 조작 확인.
- 측정: 문의·콘솔 이동·주문 연결 이벤트 중복과 개인정보 유출 없음.
- 연동: 1차는 기존 콘솔 연결 목적지 확인. 2차 API 통합은 별도 계약과 실제 승인된 테스트 증거 필요.
- 배포: 기존 사이트 백업·실제 복구 방법·전환 책임자·공개 승인 기록 존재.

검증 결과가 통과해도 자동 배포하지 않는다. 구현·독립 검증·최종 판단을 분리한다. 이번 Codex 조사·초안에 대한 Claude의 최종 검수는 아직 수행되지 않았다.
