# BACKEND-ORDER-02 — 고객별 랭크프리 계정 경계

상태: 고객 경계 로컬 구현·독립 검증 완료 / Claude 최종 검토 대기 · 기준: `main / f2f7f61`

> **후속 상태:** 사용자가 키 등록·암호화 저장·해제 백엔드를 명시 승인해 [BACKEND-ORDER-03](BACKEND-ORDER-03.md)에서 구현했다. 이 문서의 ‘저장/DB/해제 미구현’은 ORDER02 당시 범위 기록이다. 최신 프론트 계약은 [API-RANKFREE-CONNECTION](API-RANKFREE-CONNECTION.md)을 따른다. 기존 독립 검증 보고서는 당시 코드의 증거로 보존한다.

## 사용자 결정

2026-10-27 사용자가 질문에 **‘고객별 랭크프리 계정 연결’**로 답했다. 주문 계정 주체는 확정이며 더 이상 통합 계정과의 선택을 묻지 않는다. 고객A 요청은 고객A의 연결 키, 고객B 요청은 고객B의 연결 키를 사용한다. 공용 환경 키 fallback을 제거한다.

이 작업은 ORDER01의 서버 어댑터를 고객 문맥별로 분리하는 후속이다. 고객 키의 실제 등록·암호화 영속 저장·로그인/SSO·연결 해제·공개 주문·결제·DB 스키마·배포는 구현하지 않는다. 이 제한은 계정 방향이 미결이어서가 아니라 아직 해당 기능을 만들거나 검수하지 않았기 때문이다.

## 확인과 연결 원칙

[공식 API 문서](https://rankfree.kr/developers#order)를 다시 확인했다. Bearer 또는 X-API-KEY 인증과 키 소유 주문 조회가 명시되어 있다. OAuth/SSO 교환·외부 사용자 인증 엔드포인트는 공개 문서에서 확인하지 못했다. 이메일·비밀번호를 대신 받거나 OAuth 성공을 가정하지 않는다.

후속 자격증명 저장 계층은 로그인한 제이커브 고객 ID로만 연결 레코드를 찾고 암호화한 키를 복호화해 전달한다. 요청 본문이 지정한 고객 ID를 신뢰하지 않는다. 연결 등록 시 실제 키 소유 계정 증명과 order 권한 확인 방법은 공급 API 담당자와 검수해야 한다. 상품 조회 성공만으로 연결 키가 정확히 어느 사람의 랭크프리 계정인지 증명했다고 표시하지 않는다.

## 구현 계약

- `CustomerCredential`은 로컬 고객 ID와 메모리상의 키를 가진다. 키는 native `SensitiveParameterValue`로 감싸 디버그/출력에서 직접 나타나지 않게 하고 JSON에도 포함하지 않는다. 객체 자체의 직렬화/복원은 금지한다.
- `RankfreeClient::forCustomer($authenticatedCustomerId, $credential)`만으로 생성한다. 연결 없음 또는 고객 ID 불일치면 HTTP 전에 거절한다. 공용 키가 설정돼 있어도 대신 사용하지 않는다.
- 클라이언트는 요청별로 새로 생성한다. 전역/singleton 캐시·고객 간 공유를 금지한다. 고객 ID·키는 생성 뒤 바꾸지 않는다. 주문 호출·preflight·상태 조회가 같은 연결 키를 계속 사용한다.
- `config/rankfree.php`와 `.env.example`의 공용 `RANKFREE_API_KEY` 설정을 제거한다. API·주문 활성화 플래그와 검수된 상품 허용표는 기본 비활성/빈 값 그대로다. 실제 `.env`를 열거나 변경하지 않는다.
- 이 생성 시점 고객 ID 검사는 HTTP 인증이나 자격증명 레코드 소유권 검증을 대체하지 않는다. 고객 ID와 Credential을 서버 인증·저장 계층에서 신뢰할 수 있게 제공하는 작업이 남아 있다.
- 기존 가격·상태·응답 필터·리다이렉트 금지·자동 재시도 금지를 유지한다. 모의 키만으로 A/B 교차 요청·설정 변경·키 부재·직렬화·로그 출력 경계를 검증한다.

소유: `app/Services/Rankfree/*`, `config/rankfree.php`, `.env.example`, `tests/Feature/RankfreeClientTest.php`, `tests/Feature/RankfreeCustomerIsolationTest.php`, 본 문서. 프론트·DB·라우트·인증 시스템·실제 키·주문·배포·기존 검증 보고서는 변경하지 않는다.

## 검증과 인수인계

구현 → 별도 검증 세션의 고객 경계 공격·무력화 복구 → 보고서·해시 → Claude 최종 검수 순서다. ORDER01의 74/484·독립13/386 결과는 이전 버전의 증거로 보존하고 이번 변경 결과와 구분한다. 사용자 결정은 요청 큐와 대시보드에도 기록한다.

구현자 결과: 전체 **80/80 tests · 522 assertions**, 주문 관련 **20/20 · 120 assertions**, 소유 PHP Pint 통과. 독립 지시서: [BACKEND-ORDER-02-VERIFY](BACKEND-ORDER-02-VERIFY.md). 실제 API·키·계정 연결·서버를 검증한 수치는 아니다.

## 독립 검증 최종 결과

[독립 검증 보고서](BACKEND-ORDER-02-VERIFY-RESULT.md)에 실제 명령·공격 fixture·예외 출력 subprocess·해시·무력화 복구를 보관한다.

- 전체80/522, 기존 ORDER01 공격을 새 factory로 이식한 **13 tests / 385 assertions**, 추가 고객 경계 공격 **6 tests / 191 assertions** 통과.
- A/B 동일 주문번호·Fiber를 사용한 preflight A→B→POST A→B→상태 A→B 교차 호출에서도 각 키가 유지됐다. 이는 모의 응답으로 클라이언트 경계를 검증한 것이며 실제 고객 계정의 소유권 증명이 아니다.
- 별도 PHP 프로세스에서 trace 인수를 켠 상태의 예외·직렬화·복원 차단 출력 **897 checks** 통과. 이는 별도 출력 검사 수이며 PHPUnit 테스트897개로 집계하지 않는다.
- 소유 PHP6개 Pint·문법, 격리 Vite 빌드 통과. 실행 PHP8.5.8이며 서버 PHP8.3 환경은 미검증이다.
- 고객 불일치 방어를 임시 제거하면 지정 테스트 exit1로 실패했다. try/finally 원문 복구·전후 SHA256 동일 확인 후 대상 테스트가 exit0으로 재통과했다. 무력화 전후 실제 외부 연결은 없었다.

Q-011에 고객별 계정 결정·기획/화면/키 저장 설계를, Q-012에 이번 코드 최종 검토를 요청했다. 최종 제품 판단은 Claude·대웅 검수와 구분하며 고객 연결 UI/암호화 저장/인증/주문 소유권·결제/영속 중복 방지/실키·실서버·배포는 계속 후속이다.
