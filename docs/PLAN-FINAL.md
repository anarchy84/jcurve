‘최종안’은 **기획안을 한 문서로 통합했다는 의미**다. 미결 브랜드·공개 수치·상품 목록의 확정, 개발 착수, 서비스 합격 또는 공개 승인까지 받은 것은 아니다. 사용자는 **“아직 개발은 시작하지 마”**라고 지시했다. 코드·DB·서버·환경 설정·미디어·배포·발행은 이번 작업 범위에 없다.

## 1. 이번 사용자 지시로 정리된 두 가지

| ID | 확정된 방향 | 이번 통합에서 달라진 규칙 |
|---|---|---|
| U1 | **기존 URL 보존 우선** | ‘옛 주소 전부 301→클린 URL’은 기본 원칙에서 제외. 관련 콘텐츠는 원주소 200 유지를 기본으로 설계하고, 변경 필요성이 확인된 주소만 개별 301 |
| U2 | **‘순위상승’ 표현 적극 활용** | 셀프마케팅의 제목·본문·CTA·검색 콘텐츠에 사용. 표현을 일괄 금지하거나 다른 말로 치환하는 규칙은 적용하지 않음. 목표·관측 사례·보장 주장은 구분 |

사용자가 클로드와 별도로 문답 중이므로, 나머지 질문에 임의로 답하거나 같은 질문을 다시 보내지 않는다. 기존 D1~D7 번호를 유지해 §11에서 상태를 관리한다.

**기획 기준과 현재 구현은 구분한다.** U1은 이 대화의 직접 지시에 따른 계획 방향이다. 다른 세션 인수인계의 13:20 기록에는 URL 정책 보류·현재 301 구현 유지가 적혀 있다. 이번 작업에서 `LegacyRedirectSeeder`·404 훅·서버 리다이렉트는 그대로 두며, 실제 URL별 이관 계약과 코드 변경은 향후 착수 지시 후 별도로 확정한다.

## 2. 통합 결론과 포지셔닝

**제이커브는 앱 개발·직접 운영 매체·리워드 네트워크·셀프마케팅·성과형 마케팅·세일즈 도구를 연결하는 기업으로 소개한다.**

홈에서 앞세울 핵심은 리워드 네트워크·자체 앱·셀프마케팅이다. 기존 SEO·웹 제작·퍼포먼스·CPA·보유 솔루션은 사업과 검색 자산으로 유지한다. 새 사업을 강조하기 위해 기존 사업 페이지를 삭제하거나 무관한 내용으로 바꾸지 않는다.

경쟁사와의 차이는 ‘두 서비스를 다 한다’는 말만으로 설명하지 않는다. **어떤 매체에서 어떤 참여가 일어나고, 운영자가 무엇을 통제하며, 집행 뒤 무엇을 확인할 수 있는지**를 증거로 설명한다.

### 2-1. Claude의 5단 사업 구조를 채택한다

| 레이어 | 고객에게 설명할 일 | 연결할 기존 사업·자산 |
|---|---|---|
| ① 매체 | 사용자가 머무는 앱과 지면 | 자체 운영 앱·제휴 매체. 소유·운영 형태는 검증 후 구분 |
| ② 네트워크 | 광고주 행동과 매체 수익 연결 | 리워드 네트워크·오퍼월·미션 송출 |
| ③ 노출 | 검색·플랫폼·AI에서 발견되기 | SEO·AEO·GEO, 셀프마케팅, 랭크프리 등 분석 도구 |
| ④ 전환 | 참여를 문의·가입·구매 등의 성과로 연결 | 퍼포먼스·CPA·캠페인 운영 |
| ⑤ 세일즈 | 유입 이후 리드·상담·계약 관리 | 리드베이·콜투세일 등 기존 서비스 |

이 구조는 홈 중간의 사업 연결 설명에 사용한다. 첫 화면에서는 세 고객의 목적을 먼저 안내하고, CRM까지 한 번에 이해해야 시작할 수 있는 동선으로 만들지 않는다. 각 단계의 실제 제공 범위와 서비스 관계는 검증된 내용만 표시한다.

### 2-2. 차별화의 증거를 세 가지로 통일한다

1. **운영 실체:** 공개 가능한 실제 앱·스토어·미션 화면·운영 주체.
2. **집행 통제:** 직접/제휴 매체 구분, 과금·완료 인정·중복 참여·운영 대응 기준.
3. **결과 확인:** 집행량·비용과 이후 순위·문의·구매 결과를 구분한 실제 사례·데이터.

정책·품질 정보는 고객이 집행 조건을 이해하기 위한 지원 정보로 둔다. 회사의 첫 메시지를 정책 준수만으로 구성하지 않고, 검토하지 않은 상품에 ‘검토 완료·완전 안전’이라는 표시도 하지 않는다.

사용자가 원한 표현을 상품 검토가 끝날 때까지 전부 숨기는 방식은 채택하지 않는다. 다만 문구 사용과 특정 미션을 실제로 판매할 수 있는지는 다른 문제다. D4는 **순위상승이라는 단어의 사용 허가**가 아니라 **공개·주문 가능한 구체 상품 목록과 조건**을 확인하는 항목으로 정리한다.

참여 수량, 검색 순위, 매출은 서로 다른 지표다. 실제 상승 사례가 있어도 단순 전후 비교를 인과 효과로 단정하지 않는다. 실사용자 참여라는 사실만으로 모든 플랫폼 정책을 충족한다고 주장하지 않는다.

## 5. URL과 정보구조 — 보존이 기본이다

### 5-1. URL 결정 규칙

**‘옛 URL을 새 디자인에서 그대로 서비스할 수 있으면 유지한다.’** 특히 검색 유입·외부 링크가 있거나 보존할 내용이 있는 페이지는 원URL 200을 우선한다. GSC 데이터가 아직 없다는 이유로 먼저 전부 이동시키지 않는다.

| 유형 | 처리 |
|---|---|
| 관련 콘텐츠가 남는 기존 URL | 원URL에서 새 화면·본문을 제공하는 설계 우선 |
| 실제 중복·통합·기술적 변경이 필요한 URL | 이유와 대응 콘텐츠를 원장에 적고 최종 주소로 1회 301 |
| 기존 정상 주소와 새로 제안된 중복 주소 | 공개된 원주소를 우선. 중복 공개를 피하고 canonical·내부 링크를 통일 |
| 새로운 콘텐츠 | 명확하고 안정적인 신규 URL 사용. 신규 규칙을 옛 주소에 소급 강제하지 않음 |
| 더미·폐기·계정·장바구니 | 유입·기능·대응 콘텐츠를 개별 확인. 무관한 홈 일괄 이동 금지. 삭제는 별도 승인 |

기존 문서의 ‘소문자·하이픈·트레일링 슬래시 없음’은 **새 경로를 설계할 때의 관례**로만 활용한다. 기존 한글 슬러그·슬래시·쿼리 주소를 형식 통일 때문에 바꾸지 않는다.

### 5-2. 통합 페이지 지도

| 역할 | 통합 경로·처리 원칙 |
|---|---|

Claude 안의 `/services/self-marketing`, `/services/reward-network/media`, 앱별 `/solutions/…`는 이번에 모두 추가하지 않는다. 셀프 허브·매체 공개·앱 소개의 역할을 위 구조로 합쳐 중복을 줄인다. 단, 공개 배포된 주소가 실제로 존재하면 지우지 않고 URL 원장에서 별도 판단한다.

상품·셀프 랜딩과 기존 SEO 페이지가 같은 검색 의도를 중복 공략하지 않게 한다. 구분할 가치가 없으면 별도 페이지를 늘리는 대신 기존 페이지 안에서 상품·진단 경로를 연결한다.

## 6. 기존 검색 노출을 지키는 실행 순서

### 6-1. 기준선 확보

기획 단계에서 GSC 제공 시점은 D7로 남긴다. 실데이터 없이 기존 성과·상위 글·전체 색인 수를 확정하지 않는다. 향후 구현 착수 전에는 최소 보존 URL과 원문 스냅샷을 확보하고, **공개 전에는 GSC 등 실제 검색 기준선을 확보**해야 한다.

원장 항목: 원URL, 검색어, 클릭·노출·전환, 외부 링크, 현 응답, title·description·H1·본문·이미지, canonical·robots, 원발행일, 유지/이동 이유, 최종URL, 승인, 검증 결과.

공개 사이트맵·내부 링크·GSC·서버 로그·구버전·외부 유입을 합친다. 이번 Codex 조사에서 XML 6개를 중복 제거한 공개 URL은 39개였고 보관 원문은 칼럼 50개·WP 글 3개였다. 이 값은 전체 색인 수가 아니다.

### 6-2. 원문·주소를 먼저 보호하고 새 사업을 추가한다

1. 기존 URL·본문·이미지를 새 Laravel에서도 제공할 수 있게 호환 설계를 만든다.
2. 원문 단위로 보존·예외 이동을 결정한다. 현재 `LegacyRedirect`와 이관 데이터도 보존 원칙에 맞춰 검토한다.
3. 리워드·셀프 상세·앱 증거·콘텐츠 운영 기능을 비공개 환경에서 준비한다.
4. 기존 홈의 실제 검색 기여도를 보고 홈 배치·카피·title을 전환한다.
5. 꼭 필요한 URL 변경만 승인된 개별 매핑으로 처리한다.

주소가 같아도 주제·본문·내부 링크가 크게 달라지면 검색 성과는 바뀔 수 있다. 홈의 SEO 유입을 새 리워드 설명으로 한 번에 덮지 않고, 기존 SEO 전문 페이지와 접근 경로를 함께 보강한다.

### 6-3. 스테이징·공개·복구

스테이징은 인증 보호와 noindex를 함께 설계한다. robots.txt 차단만으로 비공개·색인 방지를 대신하지 않는다. 실제 dev 상태는 서버 담당자의 현황과 응답을 대조한다.

공개 전 검수는 원URL→상태 코드→최종URL→본문→이미지→canonical→내부 링크→사이트맵을 함께 확인한다. 개발 주소·잘못된 noindex·무관한 리다이렉트·비어 있는 도착 페이지는 실패다.

WordPress 교체 자체는 검색 자산을 폐기하는 행위가 아니지만 **현재 원문·기능·이미지·주소 호환 검증과 백업·복구 준비가 끝난 뒤** 판단한다. ‘워드프레스 철거 OK’를 즉시 서버 작업 지시로 해석하지 않는다.

공개 버전·DB 호환·서버 라우팅·캐시·원문 스냅샷을 묶어 복구 절차를 준비한다. 공개 승인과 서버 작업은 별도다.

필요한 301은 최소 1년 유지하고 가능하면 장기 보존한다. 같은 도메인 내 경로 변경에 도메인 이전용 Change of Address 절차를 기계적으로 적용하지 않는다. 회복 시점은 보장하지 않는다. [Google 사이트 이동 공식 문서](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

### 6-4. 공개 후 관측

- 첫 72시간: 핵심 URL·오류·noindex·canonical·문의·주문 연결 확인.
- 첫 2주: 보호 페이지의 수집·색인·클릭·노출과 리다이렉트 확인.
- 3~8주: 7일·28일·동요일·브랜드/비브랜드·기기별 비교.
- 이후: 유지 주소·이미지·리다이렉트와 검색 성과 정기 점검.

충분한 표본이 있는 보호 페이지군의 비브랜드 클릭이 7일 기준선 대비 20% 이상 하락하면 내부 조사에 착수한다. 공식 임계값이나 순위 회복 보장은 아니다. 총유입 증가로 기존 페이지 손실을 가리지 않는다.

## 7. SEO·GEO 통합 기준

아래는 두 계획과 2026-10-27에 대조한 공식 문서를 통합한 기준이다. 이 문서 작성 중 새로운 검색 계정 조회나 사이트 실측은 하지 않았다.

| 영역 | 통합 기준 |
|---|---|
| 서버 HTML | 핵심 설명·H1·가격/조건·링크는 실제 HTML에 존재 |
| 메타·정규화 | 고유 title/description, 공개 최종URL canonical, 중복·필터·UTM 규칙 |
| 사이트맵 | 공개·검색 대상 canonical URL만 포함. 실제 변경일 반영. 과거 글의 날짜 일괄 갱신 금지 |
| RSS | 최근 승인 발행 글을 제공. 기존 모델·운영 필요에 맞춰 범위 확정 |
| IndexNow | 승인된 공개 신규·변경·삭제 URL만 알림. 접수와 색인을 구분 |
| 구조화데이터 | 실제 회사·글·저자·경로·앱·서비스를 설명. 화면에 없는 수치·가격·후기 추가 금지 |
| 회사·제품 관계 | 동일 조직의 명칭·주소·연락처 일관성. 실제 소유/운영 관계를 확인하고 연결 |
| `sameAs` | 같은 대상을 식별하는 공식 URL에 사용. 회사와 서로 다른 제품을 단지 소유 관계라고 `sameAs`로 연결하지 않음 |
| FAQ | 질문 해결용으로 유지. FAQ 리치결과 확보를 목표로 삼지 않음 |
| llms.txt | 필수 범위에서 제외. Google 노출 개선 기능으로 취급하지 않음 |
| 네이버 | 서치어드바이저·사이트맵·RSS·IndexNow, 주제 일관성과 실제 경험 기반 콘텐츠 |
| AI 검색 접근 | 검색용 봇·학습용 봇 구분, robots와 CDN/WAF 함께 확인 |
| 측정 | GSC 일반 실적과 Google AI 전용 노출 보고서, 타 AI 플랫폼 표본 관측·유입을 구분 |
| 성능 | 모바일 실사용 p75 목표 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1. 실험실 점수를 실사용 결과로 표시하지 않음 |

`Article.author`를 전부 아나키로 고정하지 않고 실제 저자를 표시한다. 검수자·기준일·출처는 화면과 CMS에 남기며 지원되는 스키마 항목은 실제 타입과 검증 도구에 맞춰 정한다. 구조화데이터만으로 인용·순위가 보장된다고 설명하지 않는다.

Google AI 최적화는 특정 문단 길이·글 분할·별도 AI 파일을 필수로 요구하는 공식으로 설계하지 않는다. FAQ 리치결과는 2026-05-07 종료됐고, Google은 llms.txt가 자사 검색 노출에 영향을 주지 않는다고 명시한다. [Google AI 가이드](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide), [공식 변경 로그](https://developers.google.com/search/updates)

Google의 Search generative AI 포함 설정과 Generative AI performance report를 확인한다. 이 보고서는 Google AI 노출을 다루므로 ChatGPT·네이버 실적으로 혼용하지 않는다. [설정 안내](https://support.google.com/webmasters/answer/16908024), [AI 실적 보고서](https://support.google.com/webmasters/answer/16984139)

네이버 블로그 요약은 원문 복제가 아니라 실제 경험·작업 과정을 재구성한 별도 초안으로 준비한다. ‘민간 조사 82%’를 고정 알고리즘이나 채널 예산 공식으로 사용하지 않는다. IndexNow 성공을 상위노출 성공으로 기록하지 않는다. [네이버 콘텐츠 권장사항](https://searchadvisor.naver.com/guide/content-basic), [IndexNow](https://searchadvisor.naver.com/guide/indexnow-about)

검색봇 허용은 현재 공식 안내로 검증한다. [OpenAI 크롤러](https://developers.openai.com/api/docs/bots), [Google Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)

## 8. 데일리 콘텐츠와 관리 기능

### 8-1. 주제 운영은 Claude의 5개 축을 채택한다

| 요일 | 주제 축 | 방향 |
|---|---|---|
| 월 | 리워드·앱 수익화 | 실제 미션·매체 운영·연동·리텐션 |
| 화 | 셀프마케팅·로컬커머스 | 순위상승·플레이스·쇼핑의 실행과 측정 |
| 수 | SEO·AEO·GEO | 검색 진단·이관·원천 정보·공식 변경 해설 |
| 목 | 퍼포먼스·CPA·리드세일즈 | 비용·전환·리드 품질·실제 운영 |
| 금 | 사례·원천 데이터 리포트 | 집행 조건·결과·측정 한계를 공개 |
| 토·일 | 운영 메모·질문 답변·기존 글 개선 | 주제 축과 연결. 동일 자료를 제목만 바꿔 반복하지 않음 |

하루 1건의 유용한 콘텐츠를 목표로 하되 새로운 글 수를 채우려고 자료를 만들지 않는다. 데이터가 없으면 실제 화면·운영 과정·도구 사용·공식 출처를 갖춘 가이드를 쓸 수 있다. 모든 글에 자사 숫자 1개를 의무로 넣는 규칙은 채택하지 않는다. 데이터 리포트·성과 사례에는 표본·기간·측정 근거가 반드시 필요하다.

정의 문단 ‘40~60단어’, 질문형 H2 ‘3~5개’, 키워드 일치 앵커는 고정 합격 조건에서 제외한다. 독자 질문에 먼저 답하고 표·체크리스트·관련 링크를 필요한 만큼 사용한다. 무의미한 키워드 반복이나 지역·업종 치환 페이지 양산은 하지 않는다.

### 8-2. 초안→검토→승인→공개를 버전 단위로 관리한다

**주제·자료 → 초안 → 출처·상품·수치 확인 → 지정 검수자 승인 → 수동 공개 또는 승인된 예약 공개 → 피드 갱신 → 성과 확인**.

실행 시각이 왔다는 이유만으로 미승인 초안이 공개되면 안 된다. 승인한 뒤 본문·가격·수치 등 검토 대상이 바뀌면 승인 버전을 다시 확인한다. 예약 발행 기능의 채택·운영 권한도 향후 결정 대상이며 이번에는 스케줄러를 설정하지 않는다.

CMS는 기존 Insight 모델과 관리 구조를 확장한다. 필요한 정보는 저자·검수자·승인 버전·상태·원발행일·수정 이력·원출처·측정 방법·관련 서비스·canonical·미리보기다. Claude 안의 ‘Filament 3’는 고정하지 않고 현재 Laravel·PHP·권한 구조와 호환되는 관리 방식부터 검토한다.

노출 0이라는 이유만으로 월말에 자동 noindex·통합·삭제하지 않는다. 수집·색인·주제·링크·관측 기간을 확인하고 기존 글 보호 원칙에 따라 판단한다. 기존 칼럼 50편은 원문·주소·날짜를 보관하고 개별 유지·개선·필요한 이동을 정한다.

### 8-3. 첫 30일 편성 — 신규 글과 개선 작업을 함께 운영

Day 1은 실제 콘텐츠 운영 승인 후 첫날이다. 일정 예약이나 발행은 아직 하지 않았다.

| 일 | 제목·작업 | 연결 |

| 2 | 리워드 광고와 일반 광고, 비용이 발생하는 순간 | 광고주 |
| 3 | 플레이스 순위상승, 시작 전에 기록할 다섯 가지 | 플레이스·분석 |

## 9. 기술·주문·기존 서비스 연결

기존 Laravel 13·Blade·PHP 8.3 이상 환경을 유지한다. MySQL/MariaDB 호환과 Node의 정확한 빌드 조건은 현재 의존성과 서버 버전으로 대조한다. Next.js 전환이나 별도 CMS 서버 재구축은 통합 범위에 넣지 않는다.

1차 주문 연결의 기획 기본안은 **상품 설명 → 기존 운영 콘솔의 정확한 가입·상품·주문 화면**이다. 기존 로그인·충전·정산·파트너 체계를 중복 개발하지 않는다. D8은 실제 초기 통합 범위와 주문 주체를 확인하는 후속 항목이다.

홈페이지 내 주문을 선택할 때는 Laravel 서버에서만 기존 랭크프리 API를 호출한다. 사용자별 소유권·키 소유 계정·잔액/정산·가격 확정·중복 주문 방지·취소/환불·오류 처리를 계약으로 정한다. 문서 확인을 인증·주문 성공으로 보고하지 않는다.

공개 API의 상품 상세에는 내부용 필드가 섞일 수 있고 첨부 파일 때문에 API 주문이 불가능한 상품도 있다. 허용 상품·사용자 입력 필드를 확인 없이 전부 폼으로 노출하지 않는다. POST 타임아웃 뒤 멱등성 계약 없이 자동 재주문하지 않는다. [랭크프리 API 문서](https://rankfree.kr/developers#order)

성과 수치·법인 정보는 기존 고지와 근거를 유지한다. 자체·제휴 매체 비중과 앱 MAU는 실제 집계 전에 채우지 않는다. API 키는 서버 환경에만 두며 이번에는 키 조회·주문·충전·서버 호출 테스트를 하지 않는다.

향후 서버 반영 경로는 다른 세션 인수인계에 **개발 → GitHub 푸시 → 저장소 주소를 서버 담당자에게 전달 → 서버 담당자 반영**으로 기록돼 있다. 이번에는 이 절차를 계획에만 기록한다. 커밋·푸시·전달·서버 반영은 실행하지 않으며, 개발 보류 지시도 해제되지 않았다.

| 순위상승 카피 Codex안 채택, 상품 적합성 별도 | U2 및 D4와 일치 |
| 리워드·다이렉트·인사이트 라인명 보류 | 이름 후보는 확정하지 않으며 D1/D3 및 §3에 반영 |
| dev는 사용자 맥 curl에서 200·전체 허용·noindex 없음, Googlebot도 200 | 다른 환경의 공개 상태 관측으로 추가. Codex의 403 관측을 삭제하거나 동일 환경 재현으로 바꾸지 않음. 향후 스테이징 보호 우선 점검 |
| GitHub를 거쳐 서버 담당자가 반영 | §9의 향후 반영 경로로 기록. 이번 실행 권한·작업으로 확대하지 않음 |

Codex 세션에서 경쟁 URL 20개는 공개 페이지·DOM을 1차 확인했으며 **REA 번들 분석은 미실시**다. dev의 비로그인 HTTP 요청은 403이었고 로그인 뒤 화면을 확인하지 못했다. Claude 문서의 REA·dev 실사는 해당 세션의 관측으로 분리한다. 통합했다는 이유로 검증 범위가 늘어난 것으로 기록하지 않는다.

GSC·GA4·네이버 실계정 기준선, 전체 URL·리다이렉트 전수 검증, 실제 앱 참여·보상, 주문 인증·충전·환불, 브랜드 권리·정확한 MAU, 실제 모바일 성능은 미검증이다. 검색량·시장점유율·성과 전망을 새로 만들지 않았다.

이번 문서 검증에서는 두 입력 원본의 해시 보존, 새 문서·안내의 로컬 링크, U1/U2와 D1~D8·30일 편성·개발 보류 표시를 확인했다. `git diff --check` 종료 0, 앱·라우트·리소스·DB·public·설정·의존성 파일의 추적 변경 없음도 확인했다. 다른 세션이 갱신한 Claude 인수인계는 그대로 보존했다. 문서 검증을 앱 실행 테스트나 사이트 공개 검증으로 간주하지 않는다.
